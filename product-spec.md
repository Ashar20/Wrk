# Wrk

### A Solana-native Android network for paid physical-world data capture

**Category:** DePIN x RWA x AI x mobile  
**Status:** Android MVP specification  
**Platform:** Native Android only, Solana Mobile, Solana devnet/mainnet path  
**Name:** Wrk *(domain and trademark availability unverified)*

---

## 0. Product Thesis

Robotics and embodied AI need real physical-world observations: hands moving objects, people navigating rooms, tools being used, environments changing. Most of that data is generated by ordinary people and organizations, but there is no simple way for them to contribute it, prove what they contributed, and get paid.

Wrk turns an Android phone into a paid capture device.

The first contributor experience is deliberately simple:

```text
Open Android app -> connect Solana wallet -> choose a task
  -> record a short head-mounted episode -> upload -> validate -> get paid
```

The protocol stays asset-agnostic. A phone, robot, warehouse camera, factory sensor, or vehicle fleet can all register as data-producing assets later. The MVP starts with the device everyone already has: an Android phone.

---

## 1. Why Solana

Wrk should be built natively on Solana because the product needs fast, low-cost, high-frequency settlement for many small contributions.

The core loop is not one large transaction. It is many small events:

- asset registration
- bounty creation
- episode submission
- validation result
- reward release
- reputation update
- dataset/license record
- model utility score

Solana is a good fit because contributors can be paid quickly, rewards can be small, and mobile wallet flows can feel close to normal app UX.

Wrk should use:

- **Solana Mobile Wallet Adapter** for wallet connection, message signing, and transaction signing from the Android app.
- **Solana Mobile dApp Store** as a distribution channel for a crypto-native Android APK.
- **SPL Token / USDC** for bounty escrow and contributor payments.
- **Memo or lightweight program events** in the earliest demo, then custom Solana programs for registries and escrow.
- **Compressed NFTs or tokenized records** later for dataset/license receipts if useful.

Seed Vault is mainly relevant for wallet apps and Solana Mobile devices. Wrk should not manage user seed phrases. The app should rely on wallet apps through Mobile Wallet Adapter.

## 2. MVP Positioning

**One line:**

> Wrk lets anyone with an Android phone complete physical tasks, contribute sensor data for robotics and AI, and get paid on Solana.

**Comparison:**

> Ego4D, but mobile-native, permissionless, and paid.

Egocentric video is valuable because it shows the world from the perspective of a person doing useful physical work. Robotics researchers already use datasets like Ego4D, EgoExo4D, and Project Aria because head-mounted video teaches models about manipulation, motion, and interaction.

Wrk is not trying to prove that one hackathon app can train a robot. Wrk proves the missing coordination layer:

- contributors can capture useful episodes
- buyers can request specific physical tasks
- validators can score plausibility
- rewards can settle on-chain
- datasets can become licensable assets

## 3. Product Scope

### MVP

The MVP is a native Android app and Solana-backed demo flow. It is not a PWA, not a browser wrapper, and not a WebView-shell MVP.

Wrk is not a greenfield build. It should reuse the already-working source implementation for video capture, motion capture, episode packaging, upload flow, and validation/scoring wherever possible. The new work is the Solana-native Android wrapper, wallet/payment layer, and the Solana program surface around the existing capture pipeline.

MVP capabilities:

- connect a Solana wallet
- show wallet address and balance
- show available bounties
- request camera, microphone, motion, and optional location permissions
- record a 10-30 second physical episode
- collect synchronized video, audio, accelerometer, gyroscope, orientation, and timestamp data
- build an episode manifest
- hash the manifest and uploaded assets
- upload raw files and manifest to off-chain storage
- submit the episode hash to Solana
- run a validator service
- show plausibility score
- release testnet USDC or demo SPL reward when accepted

## 4. Android App

The Android app is the main product, not a wrapper around a web page. Build it natively in Kotlin with Jetpack Compose.

Native Android requirements:

- Kotlin Android app
- Jetpack Compose UI
- CameraX video capture
- Android SensorManager for accelerometer, gyroscope, and rotation vector
- Android permission flow for camera, microphone, motion sensors, and optional location
- Android local file storage for pending episodes
- native upload queue
- Solana Mobile Wallet Adapter Kotlin client
- Solana Kotlin transaction/RPC libraries
- signed APK for Solana dApp Store submission

Do not use:

- PWA as the main product
- WebView as the MVP app shell
- browser-only capture APIs
- embedded private keys
- direct seed phrase handling

### Contributor Onboarding

Wrk is for people doing useful physical tasks, not crypto natives. The contributor should experience Solana as the payment rail in the background, not as a concept they need to understand before earning.

Onboarding goal:

```text
Open app -> see task and payout -> tap Start
  -> approve payment account once -> record task
  -> submit -> see "You earned $0.60"
```

The contributor should not need to understand:

- seed phrases
- gas
- SOL
- SPL tokens
- wallet addresses
- signatures
- devnet or mainnet
- transaction hashes
- block explorers

Product rule:

> Crypto is infrastructure, not the interface.

Contributor-facing language:

- say `payment account`, not `wallet`, where possible
- say `approve payout`, not `sign transaction`
- say `processing payment`, not `confirming transaction`
- say `view receipt`, not `view hash`
- show earnings in dollars first
- show token/network details only in an advanced receipt view

Onboarding behavior:

- Let users browse bounties before connecting a wallet.
- Let users understand the task, reward, and recording requirements before any crypto prompt.
- Ask for wallet/payment setup only when it matters: before submission, payout, or claiming.
- If an MWA-compatible wallet is already installed, connect through Solana Mobile Wallet Adapter.
- If no wallet is installed, show a simple `Set up payment account` path and route to a supported wallet install/create flow.
- Store the MWA auth token securely so returning users do not approve every request from scratch.
- Hide gas and network fees from the main flow.
- Use sponsored fees, relayers, or app-funded fee payer flows wherever possible.
- Keep addresses, signatures, and explorer links available but secondary.
- Never ask for a seed phrase.
- Never store private keys in Wrk.

Solana Mobile helps this onboarding because Mobile Wallet Adapter lets Wrk request wallet approval from a native Android app without teaching users how key management works. On Seeker-class devices, Seed Vault can improve the wallet-side custody experience, but Wrk should still interact through Mobile Wallet Adapter and should not integrate directly with Seed Vault unless Wrk becomes a wallet app.

### Contributor Flow

```text
Install Wrk -> connect wallet -> pick bounty
  -> mount phone or hold it in first-person view
  -> record episode -> submit -> see score -> receive reward
```

The first version should feel like a field-work app, not a crypto dashboard. The contributor should always know:

- what task to perform
- how long to record
- which sensors are active
- what reward is available
- whether the capture passed
- when payment is sent

### Native Capture Advantages

Native Android improves the original browser MVP:

- better access to camera APIs
- more reliable background sensor sampling during capture
- better control over timestamping
- better file handling for large recordings
- clearer permissions UX
- APK distribution through Solana Mobile dApp Store
- possible future attestation path through Android integrity APIs

The capture UX and episode lifecycle should be modeled after the existing source app. Wrk should swap the web or previous chain-specific edges for Android-native capture and Solana submission while keeping the proven video-plus-motion workflow intact.

The app should still be honest about provenance. Native Android improves trust, but a normal app still cannot magically prove that the camera saw a real-world event. Trust improves through validation, reputation, and later device attestation.

### Episode Design

Episodes should be short by default. The target range is 10-30 seconds.

Short episodes reduce:

- contributor friction
- upload failure
- storage cost
- validation cost
- privacy risk
- review time

Each sensor stream should include monotonic timestamps so the validator can align video motion with IMU motion.

## 10. Validation

Wrk should not claim perfect proof of physical origin.

What the MVP can prove:

- the contributor wallet submitted a manifest hash
- the manifest and files were not modified after hashing
- the validator produced a score
- payment happened or did not happen according to the bounty rules

What the MVP cannot fully prove:

- that the phone saw the real world rather than a replay
- that the contributor personally performed the task
- that the environment was not staged or manipulated

### MVP Plausibility Score

The core validation check is cross-modal consistency:

> Compare visual motion in the video with motion measured by the gyroscope.

Head-mounted motion should produce correlated signals in video optical flow and IMU rotation.

This scoring path should be reused from the existing source. Wrk should not redesign scoring for the MVP unless the port exposes a clear bug. The validator interface can change to include Solana episode IDs and transaction signatures, but the scoring semantics should stay consistent so old test captures remain useful as regression fixtures.

Expected behavior:

- real head-mounted capture: high correlation
- screen replay: low correlation
- fake IMU trace: low correlation
- incomplete upload: rejected

Validation checks:

- video duration within bounty bounds
- required modalities present
- sensor sample rate sanity
- optical flow versus gyroscope correlation
- near-duplicate detection
- optional hand/object visibility score

Trust levels:

| Level | Source | Meaning |
|---|---|---|
| `self_reported` | Any upload | No validation beyond attribution |
| `heuristic` | Android app plus validator | Statistical plausibility |
| `attested` | Roadmap native attestation | Device integrity signal included |
| `hardware` | Dedicated sensor | Secure hardware provenance |

The MVP should produce `heuristic` data and label it honestly.

## 12. AI Demo

The demo should prove that contributed data can feed a model without exaggerating.

Wrk should train a small latent forward-dynamics model:

```text
frame_t -> frozen vision encoder -> z_t
imu_t   -> motion embedding -------> small GRU -> predicted z_t+k
```

Use:

- frozen CLIP or DINO-style image encoder
- small GRU or MLP dynamics head
- IMU-derived motion tokens
- held-out latent prediction error

The demo should show a data-scaling curve:

```text
Held-out latent prediction error

0.42 | *
0.38 |    *
0.35 |       *
0.32 |           *
0.30 |              *
     +----------------
       10  25  50  75 100 episodes
```

Do not claim the MVP trains a production robot policy. Claim that accepted mobile episodes can be converted into a training dataset and that more accepted data improves a small world-model proxy task.

## 13. Utility-Based Rewards

Flat payment gets supply started. Utility-based payment makes the network fairer.

MVP:

- pay a fixed amount for each accepted episode

Roadmap:

- train baseline on full dataset
- remove one contributor or contribution group
- retrain or approximate delta
- measure held-out performance difference
- distribute utility pool by normalized contribution score

Solana record:

- contributor wallet
- bounty id
- score basis points
- utility pool distribution transaction

This creates a path from "paid for uploading" to "paid for improving the model."

## 14. Federated Learning

Organizations may have valuable physical data they cannot upload.

Wrk should support federated participation:

```text
Org A local data -> local model update hash
Org B local data -> local model update hash
Aggregator -> global model hash -> eval metric -> payout
```

MVP demo option:

- stand up two mock organizations
- split captured episodes into two private partitions
- train local dynamics heads
- aggregate with FedAvg
- write update hashes and final model hash to Solana
- release round payments

Roadmap:

- secure aggregation
- differential privacy
- minimum participant thresholds
- independent trainer verification
- confidential compute

## 21. Risks

### Data Authenticity

Risk: users spoof captures.  
Mitigation: cross-modal validation, duplicate detection, reputation, future attestation.

### Privacy

Risk: video may include faces, homes, or private information.  
Mitigation: short clips, clear consent UX, local preview, deletion path, private bounties, optional redaction.

### Upload Reliability

Risk: mobile uploads fail.  
Mitigation: short episodes, resumable uploads, local retry queue.

### Payment Abuse

Risk: users farm low-quality submissions.  
Mitigation: minimum score, duplicate checks, reputation, validator bonds later.

### Overclaiming AI

Risk: demo implies production robotics training.  
Mitigation: position AI demo as a small world-model proxy task.
